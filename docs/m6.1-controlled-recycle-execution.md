# M6.1 Controlled Recycle Bin Execution

M6.1 proves one narrowly scoped mutation: a small file created and registered by the current DiskScope process can pass the existing prepare/token/execute gate and be moved to the Windows Recycle Bin. It does **not** enable cleanup of existing user files, M5 candidates, ordinary Temp files, application caches, Downloads, protected paths, or system files. M6.1 completion does not approve M6.2.

## Controlled probe ownership

`POST /api/v1/cleanup/probes` accepts an empty object and never accepts a path, directory, filename, size, or content. The server generates a process-session ID, two UUIDs and the exact path `%LOCALAPPDATA%\Temp\DiskScope\probes\<session-id>\probe-<uuid>.tmp`, then exclusively creates a fixed 64 KiB test file. Before and after directory creation it uses `lstat` to reject reparse points, non-directories and volume transitions.

SQLite v4 registers `probe_id`, process `session_id`, absolute path, creation time, size, nanosecond mtime/ctime, device, inode, a creation-nonce digest, state and failure code. A path prefix alone never grants ownership. Prepare queries the registry by both probe ID and the current process session. A manually placed file, guessed ID, old-session probe, other-user path or altered registry path cannot enter execution. Interrupted or old-session files are left in place; startup never unlinks them. Any future stale-probe action must pass an equivalent recycle gate.

## Prepare, token, and revalidation

`POST /api/v1/cleanup/probes/{probe_id}/prepare` supports only `requested_action=recycle`. Preflight verifies registry and session identity, canonical absolute path, exact session root, regular-file type, every parent, target and parent reparse attributes, volume identity, size, mtime, ctime, inode and device. It returns historical/current metadata, validation checks and the planned action. A passing plan creates a random 90-second token; SQLite stores only its SHA-256 digest.

`POST /api/v1/cleanup/execute` accepts only the token. The process-wide single-execution guard and scan check run first. Execute reloads the server-side probe and token records, checks expiry and single-use state, repeats the complete filesystem preflight, compares it with the prepare fingerprint and verifies the planned action is exactly `recycle`. Missing, changed, replaced, linked, cross-volume, expired, reused or unregistered targets are blocked before the recycle backend is called.

These path and metadata checks reduce TOCTOU risk but do not eliminate it. Python does not provide a handle-bound Shell recycle transaction. M6.1 allows the remaining risk only for a DiskScope-created, short-lived, small probe in a random per-process directory. This decision cannot be generalized to existing files.

## Windows Recycle Bin backend

The backend uses the Unicode `IFileOperation` interface, which Microsoft documents as the replacement for `SHFileOperation`. It initializes an STA, creates an `IShellItem` with `SHCreateItemFromParsingName`, sets `FOFX_RECYCLEONDELETE` with noninteractive flags, queues exactly one item, calls `PerformOperations`, and always checks `GetAnyOperationsAborted`. Microsoft notes that `PerformOperations` can report success even after an abort, so the abort check is required. Success additionally requires the original path to be absent. DiskScope does not scan `$Recycle.Bin` or elevate to find the destination record.

References:

- [IFileOperation](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-ifileoperation)
- [IFileOperation::SetOperationFlags](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-setoperationflags)
- [IFileOperation::PerformOperations](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-performoperations)
- [IFileOperation::GetAnyOperationsAborted](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ifileoperation-getanyoperationsaborted)

There is no `os.remove`, `os.unlink`, `Path.unlink`, `DeleteFile`, `shutil.rmtree`, command-shell deletion, or permanent-delete fallback in the production cleanup path. A backend error with the original path still present records `failed`, `target_mutation=none`; disappearance after an API error is recorded honestly as `unknown`. A crash after the Shell call is never guessed to be complete: an `executing` record becomes `EXECUTION_INTERRUPTED` with unknown mutation state when audit is next read.

## Audit and user wording

SQLite v3→v4 migration runs in a transaction, preserves snapshots, candidates and M6 audit rows, and adds the probe registry plus explicit execution fields: scope, probe/candidate identity, planned action, prepare and execute metadata, policy decision, token outcome, recycle outcome, result, failure code and target mutation. No plaintext token or target contents are stored.

The UI places this flow in a separate “安全执行测试” area. It shows the full generated path, creation and current metadata, token expiry, and the explicit action “移入 Windows 回收站.” A successful result says “已移入回收站” and explains that usable space might increase only after the Recycle Bin is emptied. DiskScope does not empty it and never reports recycled bytes as freed bytes.

All 929 existing visible candidates remain on the M6 historical-candidate dry-run path. The 15 Service Temp dumps under `C:\Windows`, `hiberfil.sys`, `pagefile.sys`, and `swapfile.sys` have no route to the controlled-probe backend.
