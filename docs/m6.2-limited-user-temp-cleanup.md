# M6.2 Limited User Temp Cleanup

M6.2 opens one deliberately narrow mutation path for files that already existed on the user's computer. Scanning remains metadata-only and read-only. Historical snapshots and M5 candidates are discovery records; they never authorize a filesystem change.

## Execution scope

The only real-file execution rule is `USER_TEMP_STALE_FILE_V1`. It is deny-by-default and requires all of the following:

- the request supplies exactly one persisted `candidate_id` and the candidate belongs to the saved `system_drive_c` scope;
- the normalized, component-aware, case-insensitive path is a child of the current process user's `%LOCALAPPDATA%\Temp`;
- `%LOCALAPPDATA%` must itself match `%USERPROFILE%\AppData\Local`;
- the candidate and current target are both a regular file;
- M5 category is exactly `temporary_file`, confidence is `high`, risk is `low`, and reason is `STALE_USER_TEMP_FILE`;
- snapshot and current metadata both show an mtime at least 30 days old;
- candidate size is at least 1 MiB;
- no parent or target is a symlink, junction, mount point, or other reparse point;
- every component stays on the C: volume; and
- snapshot size and mtime still equal the current target.

The 30-day threshold and 1 MiB threshold are internal V1 constants. The UI and API do not offer weaker user-selected values.

The extension denylist includes `.exe`, `.dll`, `.sys`, `.drv`, `.msi`, `.msp`, `.cab`, `.ps1`, `.bat`, `.cmd`, `.com`, `.scr`, and `.dmp`. An extension never grants eligibility. In particular, crash dumps remain blocked.

## Blocked scope

M6.2 does not process directories, directory trees, groups, other user profiles, generic AppData paths, Downloads, Desktop, Documents, application caches, `C:\Windows`, `C:\Windows\Temp`, ServiceProfiles, Program Files, Program Files (x86), ProgramData, Recovery, System Volume Information, or `$Recycle.Bin`. `hiberfil.sys`, `pagefile.sys`, and `swapfile.sys` remain permanently blocked.

The 15 known Service Temp dumps totaling about 165.5 GiB are outside the current-user boundary, use the blocked `.dmp` extension, and have no execution action.

## Prepare, confirmation, and execute

`POST /api/v1/cleanup/prepare` accepts one `candidate_id` plus `requested_action=recycle`. Extra fields are rejected, so a client cannot supply or substitute a path. Delete, permanent-delete, and candidate lists are rejected.

Prepare reloads the persisted candidate, reads current filesystem metadata with `lstat`, walks the parent chain, applies `USER_TEMP_STALE_FILE_V1`, and records an audit row. A successful prepare returns a random short-lived token valid for about 90 seconds. The database stores only its SHA-256 digest. The token is bound to the candidate, snapshot, scope, M5 rule version, execution policy, planned recycle action, category, risk, confidence, and a current fingerprint containing size, mtime, ctime, type, volume/device, file identity, and Windows attributes.

The UI shows the full path, filename, scan and current size, scan and current mtime, age, category, risk, confidence, policy ID, and the exact action “移入 Windows 回收站”. The user must actively tick the per-file confirmation checkbox. No item is selected by default.

Execute consumes one token under the process-wide cleanup mutex, rejects expired or reused tokens, reloads the persisted candidate, and performs the same complete metadata and boundary validation again. A changed size, mtime, type, identity, parent chain, reparse state, volume, policy binding, or missing target blocks the operation. A successful prior execution also blocks a second attempt. Prepare without Execute makes no change and expires naturally.

These checks reduce time-of-check/time-of-use risk; they cannot claim to eliminate every filesystem race. The narrow path, short token, repeated identity checks, single-file operation, and Recycle Bin are the primary mitigations.

## Recycle-only backend

Execution reuses the reviewed M6.1 Windows `IFileOperation` backend with `FOFX_RECYCLEONDELETE`. There is no `os.unlink`, `DeleteFile`, `SHFileOperation`, command-shell deletion, or permanent fallback. Sharing violations and lock violations become `TARGET_IN_USE`; access denied becomes `ACCESS_DENIED`. DiskScope never kills a process, closes a handle, schedules deletion on reboot, elevates, takes ownership, or changes an ACL.

Success requires both a successful Windows operation and absence of the original path. The audit records `target_mutation=recycle_bin` and `actual_action=recycle`. UI text says “已移入 Windows 回收站”; it does not promise that free space increased. Windows may allow the user to restore an item, but DiskScope provides no Undo API and does not watch the Recycle Bin.

## Concurrency and audit

Only one cleanup execution can run in the process. A running scan blocks execute, and an executing cleanup blocks a new scan. M6.2 has no batch endpoint, check-all control, directory recursion, or worker pool.

SQLite schema v5 adds stable policy and candidate context to each execution audit: `policy_rule_id`, category, risk, confidence, and actual action. Existing v4 data migrates in place. Each row retains execution ID, candidate or probe ID, snapshot ID, timestamps, path, snapshot/prepare/execute metadata, requested and planned actions, checks, reasons, backend outcome, status, failure code, final result, and target mutation. Paths are necessary audit metadata; file content is never read or stored. Historical snapshots and candidates are not rewritten after recycle. The candidate UI derives a `recycled` historical state from completed audit rows.

## Real-user-file acceptance protocol

After automated tests, the existing database is evaluated read-only. DiskScope does not rescan C: or enumerate `%TEMP%` to manufacture candidates. The report lists the count, total bytes, and up to ten eligible persisted candidates. If none qualify, that is a valid M6.2 implementation outcome. If any qualify, a person must inspect one small-to-medium, clearly temporary file in the browser and explicitly click “移入 Windows 回收站”. Codex must not call the execution endpoint in the background. At most one real file is used for first acceptance, and the user may inspect Windows Recycle Bin manually afterward.

## Known limitations and backlog

Eligibility is limited by the current persisted Top-K candidate source, so M6.2 does not attempt to clean all of Temp. Restoring a file externally is recognized only after a later scan and analysis. Network paths, other volumes, reparse paths, uncertain metadata, and unsupported objects fail closed.

The following remain separate future work and are not opened by M6.2:

- Batch Cleanup
- Directory Cleanup
- Application Cache Cleanup
- System Dump Cleanup
- Recycle Bin Management
- Undo
