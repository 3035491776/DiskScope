# v0.2.0 — Cleanup Center

## Real-world scan metadata compatibility hotfix

Windows 文件系统可能返回能正常读取大小、但无法由 Python 转换为日期的极端修改时间。扫描器现在把这种情况记录为有界的 `INVALID_FILE_METADATA` 警告：文件数量、逻辑大小和目录聚合仍正常计入，文件仍可参与按大小 Top-K；时间显示为不可用，并且不会参与当前用户 Temp 或整理索引的 oldest 选择。`skipped_count` 不会增加，扫描覆盖标记为 limited，已完成结果仍可保存为 schema v8 Snapshot。

只局部捕获 `OSError`、`OverflowError` 和 `ValueError` 的时间转换失败。根目录不可用、未处理的 I/O 错误和内部程序错误仍使扫描失败；任务级失败日志使用完整 traceback，并包含 scan ID、scope、root label、异常类型和消息。该修复不改变 Cleanup Center 授权、M8 单 worker 扫描结构、Top-K 大小排序或 Temp 10,000 hard cap。

## Product rationale

v0.1.1 解决了主要结果“看不懂”的问题，但真实用户完成扫描后仍不知道下一步。v0.2.0 在不改变 DiskScope“诊断优先”身份的前提下，增加“清理空间”闭环：扫描、分类、选择、实时复核、移入回收站、解释逐项结果。

## Three-tier model

- `SAFE_ACTIONABLE`（可处理）：只来自现有 `ExecutionPolicyEngine` 的 `eligible_for_recycle`。`USER_TEMP_STALE_FILE_V1`、30 天、普通文件、当前用户 Temp、低风险、高置信和 denylist 全部保持。
- `REVIEW_REQUIRED`（建议手动检查）：由独立 `ManualReviewPolicy` 授权，只覆盖当前用户 profile 下 Downloads、Desktop、Documents、Videos、Pictures 和 Music 中的普通文件。不会修改或冒充现有安全策略。
- `DO_NOT_TOUCH`（不建议处理）：系统/程序位置、危险类型、目录、reparse、非当前用户位置、未知或无法证明安全的项目。任何执行路线均不得覆盖。

分类只决定用户界面分组，不是执行授权。Prepare 和 Execute 都重新调用相应授权策略，客户端不能提交路径、classification 或任意执行目标。

## Safe batch flow

客户端最多提交 200 个服务器生成的 item ID。Prepare 逐项加载当前最新扫描记录、执行 live metadata/reparse/volume/type/identity 检查，并签发绑定 item set、scope、decision digest、进程 session 与 90 秒有效期的单次 batch token。Execute 再逐项检查并顺序调用 Windows `IFileOperation` + `FOFX_RECYCLEONDELETE`。没有永久删除回退。

## Manual review flow

人工检查项目不默认选择、不提供无条件全选。用户必须主动使用位置、类别、扩展名、大小、修改时间或搜索条件缩小范围，才可“选择当前筛选结果”；匹配超过 200 条时服务端拒绝选择并要求继续筛选。确认处理前仍要求额外勾选“我已经检查过所选文件，并确认不再需要”。该确认只允许进入独立 review prepare；safe 项不能借 review 路线绕过策略，review 项也不能进入 safe 路线。

## Hard deny boundaries

Windows、Program Files、Program Files (x86)、ProgramData、Recovery、System Volume Information、`$Recycle.Bin`、非当前用户 profile、目录、symlink、junction、reparse、special file 和危险扩展名一律拒绝。未知状态 fail closed。

## TOCTOU and partial success

Prepare 保存 size、mtime、ctime、mode、volume/device、file identity 和 Windows attributes 指纹。Execute 再读取并要求与 Prepare 完全一致。一个项目变化、消失、被占用或无权限时只跳过/失败该项目，其余项目继续；已成功进入回收站的项目不会因后续失败回滚。

## Recycle Bin semantics

界面只描述“移入 Windows 回收站的文件大小”，从不声称已经释放等量空间。DiskScope 不查看、恢复或自动清空回收站。

## DB migration

SQLite schema 从 v7 原位、additive 升级到 v8，新增 `triage_files` 与 Snapshot 级整理索引覆盖字段。旧 Snapshot、History、Candidates、cleanup batches、单文件审计与 controlled probes 不重建、不清空。旧 C Snapshot 的整理字段保持 NULL，界面如实提示必须在以后重新扫描才能获得完整筛选；retention 删除 Snapshot 时整理行通过外键级联删除。batch token 仍绑定当前进程 session，重启后失效；审计仍可读取。

## Triage File Index

系统盘扫描保持单次遍历。扫描器只在当前用户 Downloads、Desktop、Documents、Videos、Pictures 和 Music 中观察普通、非 reparse、同卷文件，不对 C 盘做第二次遍历，也不保存全部 C 盘文件。索引 hard cap 为 100,000 条：超过上限时确定性保留 50% largest 与 50% oldest-by-mtime，去重后按同样候选池补足。无效 mtime 仍可按大小保留，但不会伪装成旧文件。

扫描阶段只维护 bounded 内存选择，目录到个人位置的热点缓存也硬限制为 4,096 项；Snapshot 阶段使用一个事务和 `executemany` 批量写入。Snapshot 保存 `triage_observed_count`、`triage_persisted_count`、limit 与 complete/limited coverage。100,000 是在 50k/100k 基准后选择的上限：它覆盖较大的个人目录，同时避免 200,000 条对 RSS 与 SQLite 体积的翻倍压力。

索引只保存路径身份、名称、标准化扩展名、逻辑大小、可用时的 mtime、类别、个人目录组、安全展示分类、文件属性和索引时间。没有正文读取、hash、内容摘要、MFT、USN 或第二次 C 遍历。

## Category registry and smart views

扩展名由后端单一 registry 进行大小写无关分类：视频、图片、音频、文档、压缩包、磁盘镜像/虚拟机、备份、数据、日志/诊断、临时、安装/程序、开发/项目、设计/创作，以及未识别/无扩展名的“其他”。现有 `BLOCKED_EXTENSIONS` 是危险类型的唯一 canonical source；类别为 archive、video 或 backup 从不意味着安全可执行。

Cleanup Center 提供大而且很久未修改、超大文件、下载目录大文件、一年以上未修改、视频、压缩包、磁盘镜像和备份等智能视图。空视图不显示。时间文案使用“未修改”，并明确“很久未修改”不等于“肯定没用”。磁盘镜像和创作文件显示额外提醒。

## Server-side filter model

`GET /api/v1/cleanup/triage` 在后端处理位置、类别多选、扩展名多选、最小/最大大小、mtime 年龄、安全分类、文件名/路径搜索、确定性排序与 25/50/100 分页，同时返回 `matched_count`、`matched_bytes` 以及类别/扩展名/位置 facets。C 使用 `triage_files`；Temp 复用已有 bounded 10,000 metadata 与 candidate IDs，不复制第二套 Temp 行。

筛选和保存的 `safety_classification` 只是 UI 维度。执行仍只接受服务器 item ID，Prepare 重新加载记录并执行相应 policy，Execute 再做 live metadata、reparse、同卷、类型、身份和 TOCTOU 复核。客户端修改类别、扩展名、大小或 classification 不能获得授权。

## Performance impact

初版基准以 hotfix `5d8a0a8` 为 before，使用同机生成的零内容 NTFS metadata fixture；10k/50k 各 3 次取 median，100k 2 次取 median。fixture 创建不计时。初版从第一条记录维护双 heap，在纯流 50k 上开销过大，已回退并改为 cap 内顺序收集、真正溢出时一次性建 heap。下表是初版功能验收的历史结果，保留用于解释后续性能收口的起点。

最终物理 fixture 数据如下。RSS 为该进程观测峰值；读写字节是扫描阶段进程 I/O delta，SQLite persistence 另计。fixture 中每一个文件都位于可索引目录，因此这是整理索引的刻意最坏情形。

| 文件数 | before wall / CPU | final wall / CPU | final peak RSS | final persistence | final DB |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 10,000 | 0.240s / 0.234s | 0.334s / 0.328s | 31.0 MiB | 0.627s | 5.47 MiB |
| 50,000 | 1.008s / 1.000s | 1.570s / 1.516s | 64.2 MiB | 1.994s | 26.03 MiB |
| 100,000 | 2.255s / 2.180s | 3.162s / 3.109s | 102.9 MiB | 3.393s | 51.94 MiB |

初版扫描阶段的 median process read/write 均为 0；这项功能没有读取文件正文。50k 最坏 fixture 的增量为 0.562 秒，即约 11.2 微秒/被索引文件。它相对极快的 hot-cache 空文件基准是 55.7%，因此触发了性能收口。100k cap 保持不变。

100k 纯事件流初版结果为 traversal 3.416 秒、CPU 3.328 秒、peak RSS 120.1 MiB、persistence 4.094 秒、DB 74.0 MiB。更长的合成路径解释了它比物理 fixture 更大的 SQLite/RSS；两套 workload 都维持线性增长。

### Triage indexing performance closeout

使用 cProfile 对同一 50k 事件流进行定位：`selected()` 累计 2.662 秒，其中目录位置重判约 0.785 秒；扩展名归一化约 0.790 秒；时间转换累计约 1.131 秒；SQLite `executemany` 约 2.016 秒。优化后目录位置计算从约 101k 次降为约 1k 次，`selected()` 降为约 0.008 秒。扫描器现在在目录事件中缓存所属个人目录，非个人目录文件直接绕过整理索引，候选文件直接构建带 slots 的 `TriageFile` 并供最大/最旧选择共用；文件名扩展名提取省去通用路径处理。没有改变可扫描范围、类别、100k 上限、50/50 选择、去重补满或 Snapshot schema。曾评估延后 mtime ISO 转换，但持久化时仍需要该值，测试没有显示清晰的端到端收益，因此没有保留。

可重复纯事件流基准：同一生成器、同一机器，5d8a0a8 / 9040ae7 / 优化版顺序执行；每组预热一次，再测 3 次并取 wall/CPU median。持久化另测一次；文件数、目录数、逻辑大小以及索引观察/保存数在功能版与优化版一致。下表 wall 单位为秒，括号内为相对 5d8a0a8 增幅。

| 流样本 | 5d8a0a8 | 9040ae7 | 优化版 | 优化版 CPU | 优化版 peak RSS | 优化版保存数 / persistence |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 10k，全部整理 | 0.122 | 0.245 | 0.215 (+76%) | 0.203s | 37.4 MiB | 10k / 0.382s |
| 50k，全部整理 | 0.628 | 1.355 | 1.129 (+80%) | 1.125s | 76.5 MiB | 50k / 1.573s |
| 100k，全部整理 | 1.377 | 2.803 | 2.268 (+65%) | 2.266s | 119.4 MiB | 100k / 3.046s |
| 100k，15% 整理 | 1.437 | 1.586 | 1.550 (+7.9%) | 1.516s | 42.5 MiB | 15k / 0.500s |

另在**同一份**零内容 NTFS fixture 上交替运行三个版本，每版预热一次、测 3 次取 median。50k 全整理：5d8a0a8 / 9040ae7 / 优化版 wall 为 0.951 / 1.622 / 1.398 秒，优化版仍比无索引版慢 47.0%，但比功能初版快 13.8%；索引 50k 条，DB 26.03 MiB，persistence 1.222 秒。100k 混合 fixture 中 15k 文件位于 Downloads、85k 位于普通目录：三版 wall 为 1.925 / 2.208 / 2.106 秒；优化版比无索引版慢 9.4%，比功能初版快 4.6%；索引 15k 条，DB 8.52 MiB，persistence 0.403 秒。物理 fixture 的扫描阶段进程 read/write delta 均为 0；优化版 peak RSS 分别为 59.4 MiB 和 35.2 MiB。全部整理负载的主要剩余成本是每个文件必须保存的分类与路径 metadata，及其 SQLite 持久化；混合负载符合不超过 15% 的验收条件。这些 hot-cache fixture 数字不能外推为真实 C: 的固定加速或减速比例。本轮没有重扫完整 C:。
