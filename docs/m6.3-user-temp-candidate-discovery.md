# M6.3 — User Temp Candidate Discovery

M6.3 exists because a whole-C scan persists only the largest 1,000 files. Large Windows files and dumps can fill that set, so smaller old files under the current user's Temp directory may never reach Candidate Intelligence. This phase improves discovery coverage. It does not relax or automatically invoke cleanup execution.

## Fixed scope and Low-Impact scan

`current_user_temp` is a fixed backend scope. The server reads `USERPROFILE`, `LOCALAPPDATA`, and `SystemDrive`, rejects UNC and device paths, requires LocalAppData to remain inside the current profile on the system drive, and checks the path chain with `lstat`. The API accepts the scope key only; a caller cannot submit a Temp root.

The existing scanner performs the scan with one enumeration worker and `os.scandir`. It reads file-system metadata only, never opens file contents, never hashes targets, does not follow junctions, symlinks, or other reparse points, does not cross volumes, supports cooperative cancellation, and performs no elevation or ACL change. Scanner traversal does not apply cleanup age, category, confidence, or risk rules.

## Bounded persistence and coverage

The whole-C policy remains `top_k` with a 1,000-file limit. `current_user_temp` uses `bounded_scope` with a hard limit of 10,000 file records. If no more than 10,000 files are observed, every observed ordinary-file metadata record is persisted and file metadata coverage is `complete`.

If more than 10,000 files are observed, selection is deterministic and bounded: up to 5,000 largest files and 5,000 oldest files are selected, duplicates are removed, and remaining entries from the same two stable rankings fill unused positions. Ordering uses size, mtime, and relative path; selection is never random. The Snapshot reports `file_persistence_mode`, `file_persistence_limit`, `persisted_file_count`, and `observed_file_count`, and UI labels file metadata coverage as `limited` when the hard cap is reached. Directory aggregation retains its existing coverage semantics.

## Snapshot and candidate isolation

SQLite schema v6 adds the four persistence coverage fields to `scan_snapshots`. Migration from v5 runs in a transaction and derives historical counts without deleting or rewriting C snapshots, candidate runs, execution audits, or controlled probes. Temp snapshots use their own scope key, retention chain, restart restoration, history, and same-scope comparison. A Temp result cannot replace or compare directly with a C result.

Candidate Intelligence continues to consume saved Snapshot rows. Rules v1.1.0 add two deterministic rules used only when the Snapshot scope is `current_user_temp`: ordinary files of at least 1 MiB receive a high-confidence `temporary_file` classification from the fixed Temp context. A file directly under the Temp root receives low classification risk and the existing `STALE_USER_TEMP_FILE` policy context; files inside subdirectories remain high risk with `NESTED_USER_TEMP_FILE`, because installers and running applications may manage those trees. File age does not change M5 confidence or risk. Existing C rule behavior remains ordered and unchanged, and historical rules-v1.0.0 runs remain stored with their original version.

The UI can select a Temp Snapshot in Recommendations and explicitly run saved-metadata candidate analysis. It displays the M6.2 `USER_TEMP_STALE_FILE_V1` read-only eligibility count and bytes. The M6.2 requirements remain at least 30 days old, at least 1 MiB, regular file, high confidence, low risk, safe extension, current-user Temp boundary, candidate ID, revalidation, single-use token, and recycle-only execution. Dumps and executable or script extensions remain blocked. M6.3 never starts prepare, creates a token, or executes automatically.

## Acceptance and limitations

Automated fixtures cover 100 files for complete coverage and 15,000 files for the 10,000-record cap, deterministic uniqueness, cancellation, migration, scope isolation, candidate generation, and policy evaluation without execution. Real acceptance performs one user-initiated metadata-only scan of the current user's Temp directory, analyzes its saved Snapshot, and reports eligibility without clicking prepare or execute. No C rescan is required.

The hard cap can still omit files when Temp contains more than 10,000 ordinary files. Candidate results describe persisted metadata rather than current file-system authority. Batch cleanup, directory cleanup, application cache cleanup, system dump cleanup, Recycle Bin management, and Undo remain unavailable.
