# M6.4 — Eligibility Observability & Policy Diagnostics

## Purpose and boundary

M6.4 explains why a saved cleanup candidate currently does or does not match the guarded cleanup policy. It adds read-only summary, list, and candidate-detail diagnostics. It does not expand cleanup scope, prepare a candidate, issue an execution token, move a file, or change any filesystem object.

Diagnostics is not execution authority. A diagnostic decision is advisory and is based on historical candidate metadata. An eligible result only means that a candidate may enter the existing prepare flow. Prepare and execute must still re-read current filesystem metadata and enforce the full M6.2 gate.

`USER_TEMP_STALE_FILE_V1` remains unchanged: current user's `LocalAppData\Temp`, ordinary file, at least 30 days old, at least 1 MiB, `temporary_file`, high confidence, low risk, allowed extension, candidate ID only, one file at a time, and Windows Recycle Bin only. Dumps, executable or script extensions, directories, other users, application caches, protected paths, and system locations remain blocked.

## PolicyDecision model

`ExecutionPolicyEngine.evaluate` is the single source of truth for diagnostics. It returns a stable `PolicyDecision` containing:

- `policy_rule_id` and `execution_policy_version`
- `eligibility` and `allowed_actions`
- deterministic `primary_reason` and ordered `reason_codes`
- structured metadata-only `evidence`
- `evaluated_at`, `evaluation_basis`, and `execution_authority=false`

The execution policy version is `execution-policy-v1.0.0`. It is distinct from Candidate Intelligence rule versions such as `rules-v1.1.0`. Candidate rules identify and classify suggestions; the execution policy determines whether a candidate may proceed to realtime preflight.

## Reason codes and priority

Machine-readable reason codes include protected or invalid path and scope checks, unsupported object types, category/risk/confidence mismatches, blocked extensions, size and age requirements, unknown metadata, current-target changes used by preflight, and `POLICY_EVALUATION_ERROR`. A successful historical decision uses `ELIGIBLE_USER_TEMP_STALE_FILE`.

The primary reason order is fixed and safety-oriented:

1. Protected, out-of-scope, or invalid paths.
2. Unsupported types, reparse points, parent changes, or cross-volume paths.
3. Unknown or unsupported candidate classification.
4. Unknown or unsupported risk and confidence.
5. Candidate-rule and extension restrictions.
6. Minimum size and file age.
7. Missing, invalid, or changed metadata.
8. Policy evaluation failure.

Every applicable reason remains in `reason_codes`; only the highest-priority reason becomes `primary_reason`. The same candidate, metadata, policy version, and evaluation time produce the same ordered codes and primary reason.

Unknown category, risk, confidence, or modification time fails closed. An unexpected evaluation exception becomes an ineligible `POLICY_EVALUATION_ERROR`; summary evaluation continues and increments `evaluation_error_count`.

## Evidence and evaluation basis

Evidence contains only policy facts and metadata: scope, object type, logical size, age, snapshot modification time, category, risk, confidence, candidate reason, extension, and the corresponding required values. It never reads file content and never stores a content hash.

M6.4 uses `evaluation_basis=snapshot_only`. It deliberately does not call `stat` or `lstat` during diagnostics. Reparse, parent identity, volume, current size, current modification time, and target existence remain realtime prepare and execute checks. Historical metadata is not execution authority.

## Read-only API

- `GET /api/v1/cleanup/eligibility/summary?scope=current_user_temp`
- `GET /api/v1/cleanup/eligibility/candidates?scope=current_user_temp&limit=50&offset=0&filter=all&sort=size_desc`
- `GET /api/v1/cleanup/eligibility/candidates/{candidate_id}?scope=current_user_temp`

All endpoints require the local session. Scope is restricted to known saved-result scopes, and candidate detail is bound to the requested scope and latest candidate run. List output is bounded to 200 records per request. Filters and sorting accept fixed enums only; arbitrary SQL ordering is impossible.

The service batch-loads the current run, Snapshot context, and candidates, then calls `ExecutionPolicyEngine.evaluate` for each candidate. It does not run one database query per candidate and does not persist a second decision table. SQLite remains schema v6.

## Summary semantics

The summary reports evaluated, eligible, blocked, and evaluation-error counts; eligible and blocked bytes; policy and candidate-rule versions; coverage; age buckets; and two reason distributions.

`primary_reason_distribution` counts each candidate exactly once, so its candidate counts sum to `evaluated_candidate_count`. `all_reason_distribution` counts every reason on every candidate, so its counts may overlap and exceed the candidate count. Both distributions include bytes associated with each reason.

Zero eligible means only: no evaluated candidate met every current policy condition. It does not mean there are no temporary files or that the entire Temp directory has complete file-level coverage.

The real M6.3 Temp Snapshot persisted 10,000 of 26,543 observed file records, so coverage is limited. Diagnostics always exposes persisted and observed counts and the UI states that the result cannot represent an absolute conclusion about the entire Temp tree.

Nested Temp files retain the M5 high-risk classification because application subdirectories may contain live state, updater data, or managed caches. Root Temp files younger than 30 days remain blocked as recent. Dumps and executable or script extensions remain explicitly blocked. These explanations display backend decisions and saved Candidate Intelligence evidence; the frontend does not reimplement the rules.

## No mutation and known limitations

Diagnostics endpoints are GET-only. They do not call cleanup prepare or execute services, create tokens or audit execution records, write eligibility rows, scan the filesystem, or mutate target files. Existing M6, M6.1, M6.2, and M6.3 execution, audit, probe, and Snapshot behavior remains separate.

Results can become stale immediately after evaluation. Only the existing prepare and execute sequence can establish short-lived authority after current metadata, path components, file identity, reparse state, volume, and policy binding are checked again. Batch cleanup, directory cleanup, application cache cleanup, system dump cleanup, Recycle Bin management, Undo, and policy tuning remain future work.
